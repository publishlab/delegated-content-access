# Verification

This directory groups DCA verification evidence and cross-runtime conformance
material. It is not one authority class: `vectors/` and `fixtures/` are
recorded reference-produced inputs, while only `conformance-primitives/` and
`conformance-primitives-experiments/` are independent of the JavaScript
reference implementation. Implementation behavior stays in that
implementation's ordinary tests.

Recorded keys, ciphertexts, fixtures and vectors in this tree are generated
for repository testing. They are not production key material or deployment
configuration.

The reusable material here supports progressive implementation checking: an
implementer can select the narrowest relevant recorded package, adapt it at a
component or endpoint boundary, and run broader packages as its DCA support
grows. Reuse must not require importing the JavaScript reference or rebuilding
its demo setup. Each subtree states its own evidence and dependency boundary.

| Material                                                     | Evidence boundary                                                                             |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| One stock-library call with cross-runtime byte agreement     | [`conformance-primitives/`][primitives], independent of the reference                         |
| Cross-runtime evidence for an unselected construction        | [`conformance-primitives-experiments/`][experiments], independent experiment                  |
| Recorded DCA wire bytes another implementation can replay    | [`vectors/`][vectors], generated by the reference                                             |
| Recorded protocol input shared by multiple test tiers        | [`fixtures/`][fixtures], currently consumed by the JS reference                               |
| Behavior or a regression in one implementation               | That implementation's unit or component tests                                                 |
| DCA composition: actors, extensions, policy, HTTP or storage | Reference, contract, integration or product tests                                             |
| Test helpers and implementation-specific fixtures            | Beside the tests that own them                                                                |
| Named profiles, dependencies and role duty names             | [`profile-catalogue/`][catalogue], a checked projection of the profile specification          |
| Human requirements by claimed role and profile               | [`checklist--dca-v1-conformance.md`](checklist--dca-v1-conformance.md), informative checklist |
| Scoped profile support and JavaScript reference evidence     | [`claim-index/`][claims], catalogue-bounded and incomplete                                    |

## What the evidence establishes

The JavaScript suite exercises named DCA compositions. The vectors record
selected wire and intermediate bytes from those compositions. Primitive
conformance uses a separate literal corpus: selected inputs were copied from
vectors, while other cases have independent known-answer or encoding-rule
provenance. Its runs read neither the vectors nor the reference source.

A held `node/openssl` lane shows that its bridge and WebCrypto reproduce the
expected results for the covered calls and supplied parameters. Checking that
the reference uses those parameters belongs to source inspection and its
implementation tests. Agreement across the pinned runtime lanes reduces the risk of a
Node-specific expected result. The lanes span seven implementation languages,
with multiple JavaScript runtimes; several also share library ancestry,
including OpenSSL, so they are not independent cryptographic stacks.

Lane agreement tests reproducibility. Standards, specification rules and each
case's provenance establish its expected answer separately. Coverage extends
only to the selected calls and parameters. A port's implementation tests and
test bridge must separately check its DCA composition and joins; a green
bridge covers only the joins it exercises. These results support a conformance
assessment but do not establish a complete role or profile claim.

## From a profile name to evidence

The [profile specification](../docs/spec--profiles.md) defines each profile and
its dependencies. Verification material does not create or alter that
authority. It shows whether named implementations and recorded artifacts agree
with exercised requirements at one source and evidence revision.

A complete profile result must let a reader follow five links:

- **Profile closure:** the baseline and every optional dependency resolved for
  the claim.
- **Selection scope:** the claimed roles and whether the run demonstrates
  implementation support, enabled deployment behavior or one operation's
  selection.
- **Evidence packages:** the exact vectors, fixtures and
  implementation-owned tests selected for that scope. Primitive cases belong
  to the separate cross-runtime conformance suite.
- **Commands:** reproducible invocations for every selected evidence kind.
- **Result:** source revision, evidence revision, pass/fail/incomplete status
  and any omitted or unavailable lane.

The [scoped profile evidence index](claim-index/README.md) records eight current
JavaScript scenarios. Each record separates role-specific support declarations,
concrete selections, exact test evidence, package integrity and historical gaps.
The scenarios cover baseline JSON delivery, period keys, gzip with period keys,
two chain-key outputs, client-bound ECDH and RSA-OAEP compositions using period
keys and the simulated HTML carrier, plus the HTML carrier on its own. They do
not declare deployment enablement. Optional
duty applicability that the catalogue does not resolve remains visible as
unresolved; tests from another scenario cannot fill an evidence selector.

From `js/`, `pnpm run claim:evidence` runs only the unique test files
referenced by those scenarios. `pnpm run claim:all` observes all files admitted
by the JavaScript `test:unit` gate, while retaining exact scenario/test matching.
Both claim commands require Node 24.19 or newer; the ordinary package gate
uses Node 22.
Both commands validate the recorded-package inventory and run the owning
integrity checks. Integrity results do not count as role-duty evidence.
Neither command runs the independent stock-library conformance suite. Current
records are incomplete and bounded to the JavaScript reference; the three
profiles with no support declaration are explicitly reported as unclaimed.

The index preserves the old scenarios' package relationships and gap text as
historical, not-rechecked metadata. For example, the recorded period-key and
chain-prefix fixtures replay issuer/client behavior but do not replay publisher
sealing; the gzip profile has no dedicated recorded composition package; and
the HTML evidence reads a simulated root without a real browser or HTML parser.
Those limits remain attached to their scenario rather than being inferred from
package checks or tags elsewhere in the suite. The detailed evidence paths and
current scenario names are in the [index guide](claim-index/README.md).

### Select the narrowest evidence class

For each envelope algorithm and BIND form an implementation supports,
envelope evidence covers changes to each bound field, cross-kind substitution,
cross-render presentation, delimiter injection, non-canonical `renderId`,
incomplete chain geometry, decoded ECDH length, non-canonical payload or
envelope width, and RSA prefix confusion. This is informative evidence
selection guidance; the normative envelope conformance duties remain in
[sealed-key envelopes Section 8](../docs/spec--sealed-key-envelopes.md#8-versioning-and-conformance).

- A stock-library operation over supplied bytes belongs in primitive
  conformance. Its independent bridge corpus does not read this repository's
  reference implementation, vectors, or fixtures.
- An implementation component that constructs, reads, seals, opens, or checks
  DCA bytes starts with vectors. Its replayer feeds the recorded package inputs
  to that component and compares its observations with the recorded
  expectations.
- An implementation's core, endpoint or contract boundary that handles a
  recorded DCA exchange starts with fixtures. Its adapter supplies the recorded
  keys and setup, then compares that implementation's result with the
  fixture's expected observations. One fixture need not exercise the complete
  publisher-to-client-to-issuer-to-client deployment lifecycle.
- Product integration, deployment policy, HTTP routing, storage, and UI
  behavior remain in the implementation's own tests. Recorded material can
  supply their input, but it does not replace those tests.

The current JS reference is one consumer of vectors and fixtures. A different
implementation may build its own adapter or replay harness; it does not need
to import the reference or copy its test suite. A package marked
reference-only is not an interoperability obligation.

Use the narrowest owner:

1. A stock-library call over bytes belongs in primitive conformance. Its bridge
   receives no DCA field and builds no protocol value.
2. A recorded DCA wire artifact belongs in vectors. Another implementation can
   replay it, but the checked-in bytes currently come from the reference.
   `vectors/sets.txt` names the checksum and replay walk; primitive conformance
   does not read it.
3. A recorded protocol exchange reused by core, endpoint or contract tiers
   belongs in fixtures. The checked-in consumers currently use JavaScript
   bindings, and another implementation may supply its own adapter. A fixture
   supplies input and setup; each consuming tier owns its assertions.
4. Unselected cross-runtime evidence belongs in experiments. Selection moves
   domain behavior to its specification and implementation owners; it does not
   automatically add a primitive operation.
5. Implementation-specific behavior stays with that implementation's tests.

[`conformance-primitives/check`](conformance-primitives/check) runs every lane
it discovers under `conformance-primitives/`; each lane README names its
platform and binding. The primitive corpus is literal and self-contained;
provenance may name vectors that supplied bytes, but no primitive run reads
`vectors/`, `fixtures/` or the JavaScript reference.

`vectors/check-sums.sh` checks each vector set's `SHA256SUMS` and uses
`vectors/sets.txt` for the complete vector walk. The JavaScript reference owns
its explicit fixture and vector replay tier under
[`../js/test-vectors/`](../js/test-vectors/README.md).

`js/tools/make-vectors.js` regenerates the vector sets and the three
protocol fixture packages it owns: `fixtures/v1/baseline/issuer-admission/`,
`fixtures/v1/profiles/dca-profile-period-keys/issuer-admission/` and
`fixtures/v1/reference/protocol-regressions/`. Its `--check` mode, run by `pnpm test`
in `js/`, fails on regeneration drift. The separate
`js/tools/record-period-key-composition.js` owns the period-key composition
fixture; its `--check` verifies exact membership, checksums and regeneration.
The fixture's JavaScript replay supplies the actual role assertions.
`js/tools/record-chain-keys-prefix.js` separately owns the chain-key
prefix package and checks its exact membership, checksums and regeneration;
its issuer/client replay supplies the four attributed chain duties. Both
recorders preserve the actual producing commit/scenario pair when payloads
are unchanged. Integrity checks alone do not establish role duties.
