# Verification

This directory groups DCA verification evidence and cross-runtime conformance
material. It is not one authority class: `vectors/` and `fixtures/` are
recorded reference-produced inputs, while only `conformance-primitives/` and
`conformance-primitives-experiments/` are independent of the JavaScript
reference implementation. Implementation behavior stays in that
implementation's ordinary tests.

Recorded keys, ciphertexts, fixtures and vectors in this tree are generated
for repository testing. They are not production key material or deployment
configuration.

The reusable material here supports progressive implementation checking: an
implementer can select the narrowest relevant recorded package, adapt it at a
component or endpoint boundary, and run broader packages as its DCA support
grows. Reuse must not require importing the JavaScript reference or rebuilding
its demo setup. Each subtree states its own evidence and dependency boundary.

| Material | Evidence boundary |
| --- | --- |
| One stock-library call with cross-runtime byte agreement | [`conformance-primitives/`][primitives], independent of the reference |
| Cross-runtime evidence for an unselected construction | [`conformance-primitives-experiments/`][experiments], independent experiment |
| Recorded DCA wire bytes another implementation can replay | [`vectors/`][vectors], generated by the reference |
| Recorded protocol input shared by multiple test tiers | [`fixtures/`][fixtures], currently consumed by the JS reference |
| Behavior or a regression in one implementation | That implementation's unit or component tests |
| DCA composition: actors, extensions, policy, HTTP or storage | Reference, contract, integration or product tests |
| Test helpers and implementation-specific fixtures | Beside the tests that own them |

[experiments]: conformance-primitives-experiments/README.md
[vectors]: vectors/README.md

## From a profile name to evidence

The [profile specification](../docs/spec--profiles.md) defines each profile and
its dependencies. Verification material does not create or alter that
authority. It shows whether named implementations and recorded artifacts agree
with exercised requirements at one source and evidence revision.

A complete profile result must let a reader follow five links:

- **Profile closure:** the baseline and every optional dependency resolved for
  the claim.
- **Selection scope:** the claimed roles and whether the run demonstrates
  implementation support, enabled deployment behavior or one operation's
  selection.
- **Evidence packages:** the exact primitive cases, vectors, fixtures and
  implementation-owned tests selected for that scope.
- **Commands:** reproducible invocations for every selected evidence kind.
- **Result:** source revision, evidence revision, pass/fail/incomplete status
  and any omitted or unavailable lane.

No checked profile-claim index currently connects all five. Consequently, no
single command in this draft proves a complete named profile. The existing
pieces remain useful and executable, but their boundaries must stay visible:

- **Baseline JavaScript reference**
  - **Recorded bytes:** `vectors/v1/` and the entries of
    `fixtures/protocol-v1/` selected for the portable base contract.
  - **Implementation evidence:** from `js/v1/`, `pnpm test` runs source-boundary
    checks, portable contracts, base reference behavior, recorded replays and
    test-tool checks.
  - **Independent primitive evidence:** from `verification/`,
    `conformance-primitives/check` compares the literal primitive corpus across
    its runtime lanes.
  - **Limit:** these commands are separate results; the current tree does not
    emit one resolved `dca-v1-direct-https` claim record.
- **Exact-period behavior**
  - **Recorded bytes:** exact capabilities and wraps occur in current baseline
    vectors and protocol fixtures.
  - **Implementation evidence:** exact production, delivery, caching and item
    opening run in the JavaScript base and contract lanes.
  - **Limit:** exact-period delta evidence is not yet separated under a named
    profile package or selected by one `dca-v1-exact-period` command.
- **Period-chain behavior**
  - **Recorded construction bytes:**
    `vectors/v1-profile--period-chain-primitives/` records the current
    construction inputs and outputs; `vectors/check-sums.sh` verifies that the
    checked-in set still carries its recorded bytes.
  - **Implementation evidence:** from `js/v1/`,
    `pnpm run test:reference:extension:period-chain` exercises publisher,
    issuer and client period-chain behavior owned by that implementation.
  - **Composition evidence:** `pnpm run test:reference:compositions` exercises
    checked-in interactions between period-chain and other optional behavior.
  - **Independent primitive evidence:** the primitive-conformance corpus
    includes the literal HKDF inputs used to compare runtime outputs; it does
    not build DCA chain contexts or prove the profile composition.
  - **Limit:** these pieces do not yet resolve baseline plus exact-period plus
    period-chain into one role-scoped claim record.

A passing result therefore means only that the named command held over its
declared inputs and boundary. A vector replay does not prove policy or an end-to-end
deployment; an implementation test does not prove independent
interoperability; primitive agreement does not prove DCA context construction.
The planned checked claim index will compose these results without erasing
those distinctions.

## Choose evidence by the boundary under test

- A stock-library operation over supplied bytes belongs in primitive
  conformance. Its independent bridge corpus does not read this repository's
  reference implementation, vectors, or fixtures.
- An implementation component that constructs, reads, seals, opens, or checks
  DCA bytes starts with vectors. Its replayer feeds the recorded package inputs
  to that component and compares its observations with the recorded
  expectations.
- An implementation's core, endpoint or contract boundary that handles a
  recorded DCA exchange starts with fixtures. Its adapter supplies the recorded
  keys and setup, then compares that implementation's result with the
  fixture's expected observations. One fixture need not exercise the complete
  publisher-to-client-to-issuer-to-client deployment lifecycle.
- Product integration, deployment policy, HTTP routing, storage, and UI
  behavior remain in the implementation's own tests. Recorded material can
  supply their input, but it does not replace those tests.

The current JS reference is one consumer of vectors and fixtures. A different
implementation may build its own adapter or replay harness; it does not need
to import the reference or copy its test suite. A package marked
reference-only is not an interoperability obligation.

Use the narrowest owner:

1. A stock-library call over bytes belongs in primitive conformance. Its bridge
   receives no DCA field and builds no protocol value.
2. A recorded DCA wire artifact belongs in vectors. Another implementation can
   replay it, but the checked-in bytes currently come from the reference.
   `vectors/sets.txt` names the checksum and replay walk; primitive conformance
   does not read it.
3. A recorded protocol exchange reused by core, endpoint or contract tiers
   belongs in fixtures. The checked-in consumers currently use JavaScript
   bindings, and another implementation may supply its own adapter. A fixture
   supplies input and setup; each consuming tier owns its assertions.
4. Unselected cross-runtime evidence belongs in experiments. Selection moves
   domain behavior to its specification and implementation owners; it does not
   automatically add a primitive operation.
5. Implementation-specific behavior stays with that implementation's tests.

[`conformance-primitives/check`](conformance-primitives/check) runs every lane
it discovers under `conformance-primitives/`; each lane README names its
platform and binding. The primitive corpus is literal and self-contained;
provenance may name vectors that supplied bytes, but no primitive run reads
`vectors/`, `fixtures/` or the JavaScript reference.

`vectors/check-sums.sh` checks each vector set's `SHA256SUMS` and uses
`vectors/sets.txt` for the complete vector walk. The JavaScript reference owns
its explicit fixture and vector replay tier under
[`../js/v1/test-vectors/`](../js/v1/test-vectors/README.md).

`js/v1/tools/make-vectors.js` regenerates `vectors/` and `fixtures/` from the
reference implementation; the checked-in bytes match its output.
