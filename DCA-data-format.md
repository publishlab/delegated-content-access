## Scope

This document defines the publisher → client wire format: the markup delivered to the browser. This is the normative part of DCA - what publishers produce and clients consume. How the client unlocks and decrypts (unlock request/response, transport modes) is reference material, not part of this document. Issuers choose their own transport and delivery method.

The markup is identical for all users and designed to be cached at the edge. Sealed content and sealed keys do not vary per request - access control happens at unlock time, not render time.

DCA uses "sealed" for encrypted/wrapped data (opaque, unusable without a key) and "unlocked" for the reverse operation (issuer returns usable keys to the client).

**Binary encoding:** All binary values in DCA are base64url-encoded strings ([RFC 4648 §5](https://datatracker.ietf.org/doc/html/rfc4648#section-5), no padding). This applies throughout: dca-data (nonces, sealed content ciphertext, sealed key blobs), unlock responses (key material), and any other exchange of binary data. Exception: `aad` is a UTF-8 string (human-readable, convert via `TextEncoder.encode()`).

Decode and encode - standard base64 with URL-safe alphabet and no padding. Any language with base64 support can implement these. JavaScript example:

```javascript
function base64urlDecode(s) {
    const b = atob(s.replace(/-/g, '+').replace(/_/g, '/') + '=='.slice(0, (4 - s.length % 4) % 4));
    return Uint8Array.from(b, c => c.charCodeAt(0));
}

function base64urlEncode(buf) {
    // Note: spread operator limits input to ~65KB. For larger inputs (content ciphertext),
    // chunk the buffer: for (i = 0; i < bytes.length; i += 8192) s += String.fromCharCode(...bytes.subarray(i, i + 8192))
    const s = btoa(String.fromCharCode(...new Uint8Array(buf)));
    return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}
```

Note: `base64urlDecode` also handles standard base64 input (the replacements are no-ops when no `-` or `_` are present). PEM key import examples in [DCA-issuer-reference.md](DCA-issuer-reference.md) use it for standard base64.

### Actors

| Actor | Role |
|-------|------|
| **Publisher** | Encrypts content, seals keys for issuers, delivers markup |
| **Issuer** | Holds private key, makes access decisions, returns unlocked keys |
| **Client** | Requests unlock, decrypts content, renders to page |

### Key glossary

| Term | What |
|------|------|
| `contentName` | Publisher-defined name for a content item, e.g. `bodytext`. ASCII identifier (`[a-zA-Z][a-zA-Z0-9-]*`). Same name across articles shares periodKey derivation. |
| `contentKey` | Symmetric key (AES-256-GCM). Encrypts a single content item. Randomly generated, unique per render. |
| `periodKey` | Symmetric key (AES-256-GCM). Wraps contentKeys. Shared across articles within a time period. Derived by publisher from `periodSecret` via HKDF. |
| `sealedContentKeys` | contentKeys sealed with periodKeys (AES-256-GCM). Each entry is an object with `t` (period timestamp), `nonce`, and `key`. |
| `issuerData` | Map of `<issuerName> → issuer block` (unlock URL, keyId, sealed keys). Client forwards one selected issuer block to issuer. |
| `issuerName` | Canonical issuer identifier. It is the key name under `issuerData` and is forwarded in unlock requests for routing and context binding. Stable ASCII token, publisher-defined at onboarding (publisher ensures uniqueness across issuers). |
| `keyId` | Identifies which issuer private key unlocks `issuerData.*.sealed`. Opaque string, issuer-chosen. For key rollover - see [DCA-issuer-reference.md](DCA-issuer-reference.md#prerequisites-issuer-keypair). |
| `renderId` | Random base64url string (minimum 8 bytes / 11 characters), generated by publisher per render. Binds `resourceJWT` and `issuerJWT` - issuer verifies both carry the same value. Opaque - issuer must not assume a fixed length (publisher may increase). Fresh per render. |
| `resourceJWT` | Signed JWT (payload = `resource`). Issuer verifies publisher origin, then trusts JWT payload claims for access decisions. |
| `issuerJWT` | Map of `issuerName` to signed JWT (ES256). Issuer verifies blob integrity before unsealing - prevents content item relabeling. Client forwards one entry in the unlock request. See [issuerJWT payload](#issuerjwt-payload). |
| `t` | Period start timestamp. Format: `YYMMDDTHH` (hourly, e.g. `"251023T13"`) or `YYMMDDTHHMM` (sub-hour). Lexicographically sortable. Bookkeeping only: cache dedup, sort, evict. Not for verification - neither client nor issuer parses or validates it. |
| `periodSecret` | Publisher-held secret. Input to HKDF for deriving periodKeys. Never leaves the publisher - not in markup, not in unlock requests. |
| `contentSealData` | Per-content-item decryption parameters: content type, nonce, and AAD. |

### Field reference

| Field | Type | Consumer | Purpose |
|-------|------|----------|---------|
| `version` | string | Both | Format version |
| `resource` | object | Issuer (client forwards) | Publisher metadata (renderId, domain, resourceId, article data). `resource.data` follows the publisher's data schema (field names and structure are publisher-defined). `resourceJWT` is authoritative for access decisions |
| `resourceJWT` | string | Issuer | Signed `resource`. Issuer verifies signature, uses JWT payload for access decisions |
| `issuerJWT` | object | Issuer | Map of `issuerName` to ES256-JWT. Payload: `renderId` + `issuerName` + `proof` (SHA-256 hashes of sealed blobs). For blob integrity |
| `contentSealData` | object | Client | Per content item: `contentType` (MIME type), `nonce` (AES-GCM iv), `aad` (AES-GCM additionalData) |
| `sealedContentKeys` | object | Client | Per content item: array of `{ t, nonce, key }`. `t` is the period bucket (see [Key glossary](#key-glossary)), `nonce` for unwrapping, `key` is the sealed contentKey |
| `issuerData` | object | Both | Map keyed by `issuerName`. Each entry contains: |
| `issuerData.*.sealed` | object | Issuer | Map of `contentName` to sealed keys (`contentKey`, `periodKeys[t]`). Publisher seals both `contentKey` and all `periodKeys` for every content item granted to an issuer. The issuer chooses which to return. Issuer unseals with private key |
| `issuerData.*.unlockUrl` | string | Client | Issuer's unlock endpoint URL |
| `issuerData.*.keyId` | string | Issuer | Selects which private key to use (see [Key glossary](#key-glossary)) |

### Nonces and AAD

All nonces and AAD are precomputed by the publisher and shipped in dca-data. No client-side derivation.

| Value | Location | Used for |
|-------|----------|----------|
| Content decryption nonce | `contentSealData[contentName].nonce` | AES-256-GCM iv for content decryption |
| Content decryption AAD | `contentSealData[contentName].aad` | AES-256-GCM additionalData for content decryption |
| periodKey nonce | `sealedContentKeys[contentName][i].nonce` | AES-256-GCM iv for unsealing contentKey |

Each nonce is a random 12-byte value (base64url-encoded), generated by the publisher at render time. One nonce per ciphertext - standard AES-256-GCM practice. AAD is an opaque string - do not parse it. The `|` delimiters are for readability in devtools. Pass the value as-is to AES-GCM via `TextEncoder.encode()`. The format is a publisher implementation detail (see publisher reference).

Note: sealed blobs in `issuerData.*.sealed` are opaque to the client and contain algorithm-specific internals (nonces, ephemeral keys). Only the nonces above are client-visible.

`sealedContentKeys` unwrap uses no AAD - the nonce alone is sufficient since periodKeys are already content-specific (derived with `contentName` as HKDF salt).

`sealedContentKeys[*].key` wraps a 32-byte AES key with AES-GCM (16-byte auth tag): 48 bytes total, encoded as a 64-character base64url string.

### Key hierarchy

Three keys form a chain. To reach content, reverse the chain:

Conceptual overview: [README.md#key-layers](README.md#key-layers).

<pre>
<b>content</b>
  ← sealed with <b>contentKey</b>        (unique per content item per render)
    ← sealed with <b>periodKey</b>       (shared across articles within a time period)
      ← sealed with <b>issuerPublicKey</b>  (only issuer can unlock)
</pre>

Two paths through the chain, chosen by the issuer per request:
- **contentKey delivery** - issuer returns `contentKey` directly. Client decrypts. One unlock per article.
- **periodKey delivery** - issuer returns `periodKey`. Client unwraps `contentKey` from `sealedContentKeys`, then decrypts. periodKey is cacheable across articles - fewer unlocks.

**Where each key appears in markup:**

| Key | Markup location | Sealed with | Consumer |
|-----|-----------------|-------------|----------|
| contentKey | `issuerData.*.sealed.*.contentKey` | issuerPublicKey | Issuer (unwraps, may return to client) |
| contentKey | `sealedContentKeys.*[]` | periodKey | Client (unwraps with cached periodKey) |
| periodKey | `issuerData.*.sealed.*.periodKeys[t]` | issuerPublicKey | Issuer (unwraps, may return to client) |

**Why two periodKeys per content item?** periodKeys rotate by time period (e.g., hourly). Markup includes current + next (`h13`, `h14`) so that articles cached across a period boundary remain decryptable. The client tries each in order - first success wins. `t` is bookkeeping, not validation - see `t` in [Key glossary](#key-glossary).

**Key correspondence:** `sealedContentKeys[contentName]` entries and `issuerData.*.sealed[contentName].periodKeys` keys represent the same periods. `sealedContentKeys` entry with `t: "251023T13"` is unwrapped by the key from `periodKeys["251023T13"]`. Both use `t` as the key - no positional mapping needed.

### Example conventions

Placeholder values use angle brackets with double-dash separators:
- `<contentKey--sealed-with--periodKey-h13>` - shows relationship between keys
- Qualifiers (contentName, resourceId) are omitted when implied by context

### Page placement

One DCA instance per page. Both elements go in the `<body>`. No ordering requirement - the client finds them by class name. They can appear anywhere in the page and do not need to be siblings.

- `<script type="application/json" class="dca-data">` - inert (JSON, not executable)
- `<template class="dca-sealed-content">` - inert (`<template>` content is not rendered or executed)

### Sealed content

Each content item is encrypted with its own contentKey. Content is opaque ciphertext (base64url-encoded), placed in `<div>` elements inside an outer `<template>` (inert - prevents accidental rendering).

Attribute `data-dca-content-name` identifies the content item for key lookup and placement after decryption. Access via `template.content.querySelector('[data-dca-content-name="..."]')`.

```html
    <template class="dca-sealed-content">
        <div data-dca-content-name="bodytext">k7Hs9dF2mNqR4xPw...</div>
        <div data-dca-content-name="premiumtext">Ym3pTvKsL8nWjEcQ...</div>
        <div data-dca-content-name="locked-data">xR5fAhNt0gPkBwU7...</div>
    </template>
```

**Deferred content:** A content item may have keys in `dca-data` but no sealed blob in the initial markup. The content item's element is absent from `dca-sealed-content` and a URL provides the ciphertext. Fetched ciphertext is decrypted with the same contentKey, nonce, and AAD. Delivery format TBD.

### Signed envelopes

Two JWTs, different scopes. Both use ES256 (`{ "alg": "ES256", "typ": "JWT" }`). Both carry `renderId` - the issuer verifies they match, binding resource claims to the correct sealed keys.

- **`resourceJWT`** - signs `resource` (publisher metadata). Shared across all issuers. Issuer verifies publisher origin and reads claims for access decisions.
- **`issuerJWT`** - per-issuer, top-level map keyed by `issuerName`. Signs `proof` (SHA-256 hashes of sealed blobs). Issuer verifies blob integrity before unsealing - prevents content item relabeling.

DCA uses JWT solely as a signed JSON envelope - standard signature verification with standard libraries. No standard JWT claims (`iss`, `sub`, `iat`, `exp`) are used. If a JWT library auto-adds claims like `iat`, ignore them.

Top-level `resource` in `dca-data` is unsigned. The issuer uses `resource.domain` for signing key lookup (before JWT verification), then verified JWT payloads for all decisions: `resourceJWT` for access, `issuerJWT` for blob integrity.

Examples below show decoded JWT payloads (what the issuer sees after verification).

#### resourceJWT payload

JWT payload equals the `resource` object - no wrapper key (`resource.renderId` = `resourceJwtPayload.renderId`). All fields are required:

| Field | Purpose |
|-------|---------|
| `renderId` | Binds to `issuerJWT` (issuer verifies match) |
| `domain` | Publisher identification (issuer selects signing key) |
| `issuedAt` | Render timestamp (debug metadata, not a validity window) |
| `resourceId` | Publisher's article identifier |
| `data` | Publisher-defined metadata for access decisions (structure varies by publisher) |

```json
{
  "renderId": "<renderId>",
  "domain": "www.news-site.com",
  "issuedAt": "2025-10-23T14:00:00Z",
  "resourceId": "123456",
  "data": {
    "date.published": "2025-10-20T10:30:00Z",
    "section": "politics",
    "tags": [
      "breaking",
      "elections",
      "analysis"
    ],
    "fields.extractedCustomField1": "customValue"
  }
}
```

#### issuerJWT payload

One JWT per issuer. `proof` mirrors the shape of `issuerData.*.sealed` - same structure, hashes instead of sealed blobs. Prevents a client from swapping sealed blobs between content items to bypass access policy.

```json
{
    "renderId": "<renderId>",
    "issuerName": "<issuerName>",
    "proof": {
      "bodytext": {
        "contentKey": "<hash-of-sealed-blob>",
        "periodKeys": {
          "251023T13": "<hash-of-sealed-blob>",
          "251023T14": "<hash-of-sealed-blob>"
        }
      },
      "premiumtext": {
        "contentKey": "<hash-of-sealed-blob>",
        "periodKeys": {
          "251023T13": "<hash-of-sealed-blob>",
          "251023T14": "<hash-of-sealed-blob>"
        }
      }
    }
}
```

Each hash value is `base64url(SHA-256(base64urlString))` - hash the base64url string as-is from JSON (UTF-8 bytes), not the decoded binary. 32-byte digest, 43-character base64url string (no padding). Verification is string equality: issuer hashes the received string and compares to the signed proof.

**Seal algorithms:** `ECDH P-256` (recommended) or `RSA-OAEP` (SHA-256, 2048+ bit key). Per-issuer - the publisher seals with the algorithm matching each issuer's public key. The algorithm is not in the wire format - the issuer knows its own key type. See [DCA-issuer-reference.md](DCA-issuer-reference.md#prerequisites-issuer-keypair) for key generation.

**Sealed blob integrity (`issuerJWT`):** Each issuer's `issuerJWT` entry signs a proof - SHA-256 hashes of that issuer's sealed blobs. The issuer verifies request blobs against this signed proof before unsealing. Prevents content item relabeling (moving a sealed blob from one content item to another in the unlock request).

Proof path (inside verified `issuerJWT` payload):
- `proof[contentName].contentKey` → hash of `issuerData.<issuerName>.sealed.<contentName>.contentKey`
- `proof[contentName].periodKeys[t]` → hash of `issuerData.<issuerName>.sealed.<contentName>.periodKeys[t]`

Hash input:
- Take the base64url string as-is from JSON (do not decode)
- Compute `SHA-256(UTF-8 bytes of the string)`
- Encode digest as base64url (43 chars, no padding)

Verification rule:
- Any hash mismatch => reject entire request (integrity failure). Do not attempt partial unseal.

*Detail:* `sealedContentKeys` and `contentSealData` are not signature-covered - they are shared across issuers and consumed by the client, not routed through `issuerJWT`. Integrity is provided by AES-GCM authentication: tampering with nonces, AAD, or wrapped keys causes decryption failure (auth tag mismatch), not silent substitution.

### Sealed blob format

Each value in `issuerData.*.sealed.*` is a self-contained blob (base64url-encoded). The issuer decodes and unseals with its private key.

**RSA-OAEP:** Standard RSA-OAEP ciphertext. Single `crypto.subtle.decrypt` call. No internal structure to parse.

**ECDH P-256:** Concatenation of fixed-size fields, no length prefixes:

| Offset | Length | Field |
|--------|--------|-------|
| 0 | 65 bytes | Ephemeral public key (uncompressed P-256 point) |
| 65 | 12 bytes | IV (AES-256-GCM nonce) |
| 77 | remaining | Ciphertext + 16-byte GCM auth tag |

The publisher generates a fresh ephemeral keypair per seal. The issuer computes ECDH key agreement (ephemeral public key + issuer private key). The raw ECDH shared secret (x-coordinate, 32 bytes for P-256) is used directly as the AES-256-GCM key - no KDF. Decrypts the ciphertext using the IV. For key material (32-byte AES-256 key): ciphertext + tag = 48 bytes, total blob = 125 bytes.

```javascript
function parseSealedEcdhBlob(blob) {
    return {
        ephemeralPublicKeyRaw: blob.slice(0, 65),
        iv: blob.slice(65, 77),
        ciphertext: blob.slice(77)
    };
}
```

### Size estimate

Typical config: 3 content items, 3 periodKeys per item (current + next + one extra for overlap; examples use 2 for simplicity), 1 issuer (ECDH P-256).

**dca-data JSON overhead:**

| Section | Items | Per item | Subtotal |
|---------|-------|----------|----------|
| `version` | 1 | 15 B | ~15 B |
| `resource` | 1 | ~250 B | ~250 B |
| `resourceJWT` (ES256, payload=`resource`) | 1 | ~600 B | ~600 B |
| `issuerJWT` (ES256, per issuer, payload=`proof`) | 1 | ~500 B | ~500 B |
| `contentSealData` | 3 | ~100 B | ~300 B |
| `sealedContentKeys` | 3 × 3 entries | ~110 B (`t` + nonce + 64-char key) | ~1,000 B |
| `issuerData` sealed (ECDH) | 12 blobs (3 items × 4 keys) | ~167 B | ~2,000 B |
| `issuerData` metadata | 1 issuer | ~80 B | ~80 B |
| JSON structure | | | ~200 B |
| **Total dca-data** | | | **~4.9 KB** |

RSA-OAEP: sealed blobs are ~342 B each instead of ~167 B → issuerData grows to ~4.1 KB, total ~7.4 KB.

**Sealed content (ciphertext):**

AES-256-GCM adds a fixed 16-byte auth tag. Base64url encoding adds ~33%. No other overhead.

| Plaintext | + auth tag | Base64url | Overhead |
|-----------|-----------|-----------|----------|
| 1 KB | 1,040 B | ~1.4 KB | +0.4 KB |
| 5 KB | 5,136 B | ~6.7 KB | +1.7 KB |
| 20 KB | 20,496 B | ~26.7 KB | +6.7 KB |
| 50 KB | 51,216 B | ~66.8 KB | +16.8 KB |

**Full page example** (5 KB bodytext + 2 KB premiumtext + 0.5 KB locked-data):

| Component | Size |
|-----------|------|
| dca-data JSON | ~4.9 KB |
| Sealed bodytext | ~6.7 KB |
| Sealed premiumtext | ~2.7 KB |
| Sealed locked-data | ~0.7 KB |
| **Total DCA payload** | **~15.0 KB** |
| Original plaintext | 7.5 KB |
| **Overhead** | **~7.5 KB** (~100%) |

The overhead is dominated by base64url encoding (33% of content size) and the dca-data envelope (fixed ~4.9 KB, including signed JWTs). For larger articles the base64url 33% dominates; for small articles the fixed envelope dominates.

### JSON API variant

For API responses (headless CMS, mobile apps, SPAs), the HTML split is unnecessary. All data fits in a single JSON object. Sealed content moves into a `sealedContent` field - keyed by contentName, values are base64url ciphertext. Place it at the end so metadata comes first and large blobs last:

```json
{
    "version": "1",
    "resource": "{ ... }",
    "resourceJWT": "...",
    "issuerJWT": "{ ... }",
    "contentSealData": "{ ... }",
    "sealedContentKeys": "{ ... }",
    "issuerData": "{ ... }",
    "sealedContent": {
        "bodytext": "k7Hs9dF2mNqR4xPw...",
        "premiumtext": "Ym3pTvKsL8nWjEcQ...",
        "locked-data": "xR5fAhNt0gPkBwU7..."
    }
}
```

Note: `"{ ... }"` values are placeholders for the full objects shown in the dca-data example above. Same structure, same types - not strings.

Same keys, same nonces, same crypto chain. Only the extraction changes - for markup, the client reads two elements:

```javascript
const dcaData = JSON.parse(document.querySelector('.dca-data').textContent);
const sealedOuter = document.querySelector('template.dca-sealed-content');
// sealed ciphertext: sealedOuter.content.querySelector('[data-dca-content-name="bodytext"]').textContent
```

For JSON API, it's the object directly - `sealedContent[contentName]` replaces the DOM query.
